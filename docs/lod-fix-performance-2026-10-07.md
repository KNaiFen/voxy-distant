# 0.2.27 节点及缓存版本修复：基线性能对照

## 结论

比较 0.2.26（`dd21d22`）与 0.2.27（`69c9883`），客户端正常静止、空缓存接收及 160 方块/秒往返没有测到明显的持续渲染退化。高速阶段平均渲染调用耗时差异不到 1%，整帧 P99 差异不到 0.04 ms。节点线程仍只消耗约 0.0055 个逻辑核。

服务端存在可测成本：首次往返进程 CPU 增加约 0.054 个逻辑核（8.8%），反复往返增加约 0.099 个逻辑核（27.3%）。反复往返平均 tick 从 1.496 增至 1.522 ms，P99 从 2.042 增至 2.161 ms。这来自原版新版本持久失效及必要的缓存刷新，不能描述成零开销。此单玩家场景绝对开销较小；不能直接外推至多人连续高速旅行。

空客户端首次接收的收敛窗口从平均 14.40 增至 16.44 秒（约 14.2%）。它包括命令响应、接收、网格排空及约 3 秒空闲确认，时间边界每秒采样；不是精确的首帧延迟。两版本均摄入 1480 列远程回复并满足 1793 列全半径精度。不能仅依据新版本较低的窗口平均 CPU 宣称下载更快。

本轮只增加测试采样、可重复 A/B 入口和报告，生产代码及 0.2.27 安装包未改动。

## 方法与可比性

- 硬件：Ryzen 7 9700X，8 核/16 线程，63.6 GiB 内存；RTX 4070 Ti SUPER，驱动 610.88。客户端与专用服务端在同一主机，经 loopback 连接。
- Forge 47.4.20、Voxy 0.2.15-beta、Embeddium 0.3.31、Java 21.0.7；每 JVM `-Xms1G -Xmx4G`，窗口 1280×720，无光影。
- 原版客户端距离 10，服务端视距 8、模拟距离 2；VD 半径 24、分级 `8:0,16:1,24:2`、窗口 512、接收 128 MiB、索引 256 MiB、接收占空比 0.9。服务端 CUSTOM 4 转换线程、并发 32、8192 列/秒、快照 2 ms/tick、30 Mbps。Voxy 8 服务线程、细分尺寸 64、`ingest_enabled=false`。
- 从已保留基线只提取原点四个 region 和 `level.dat`，输入共 46,909,359 字节。每轮恢复同一输入，清除非玩家实体、关闭实体生成与随机 tick、固定时间天气，重新导入 4096 列服务端缓存；客户端没有 `.voxy`。原测试基线及用户真实实例未写入。
- 顺序 `old,new,new,old,old,new`，每版本 3 轮。每轮首次连接预热 10 秒；接收结束后测首次往返、静止 45 秒和再次往返。路线区块 `(7,0),(-7,0),(0,0)`，首次 14 次、再次 20 次，速度 160 方块/秒。服务端位置样本验证真正经过两端。该路线使接收半径仍在已保存 64×64 区块内。
- 服务端允许加载/生成缺失数据，以完成被正确失效的缓存刷新。禁止生成的预试中，新版停止后有 4 列真实 unavailable，旧版又可能误用旧缓存，因此该预试不作为完整工作量性能对照。
- 关闭 `voxy.verifyNodeManager`、节点诊断、GPU 同步回读、debug、过程录制；测量窗口不截图、不做覆盖扫描。保留两边相同的轻量帧、tick、线程和传输采样。覆盖扫描只在窗口外。
- 游戏设置实测 `vsync=false`、窗口帧率上限 260，但实际整帧稳定约 13.33 ms（75 FPS）。显示/驱动端限制的具体来源未查明，因此整帧平均值不能证明最高 FPS 无损。另测 Forge `RenderTick START→END` 的渲染调用耗时及进程/线程 CPU；该计时不包含显示等待，也不是完整 GPU 时间或完整一帧。

表格为三个回合各自统计值的算术平均，P95/P99 不是把所有帧合并后再取分位数。共 71,681 个游戏帧、18,969 个服务端 tick。CPU 单位为等效逻辑核：1.0 表示每秒使用 1 秒进程 CPU 时间。

## 客户端

| 场景 | 渲染调用平均 ms：旧 → 新 | 渲染调用 P99 ms：旧 → 新 | 整帧 P99 ms：旧 → 新 | 客户端 CPU 逻辑核：旧 → 新 |
| --- | --- | --- | --- | --- |
| 空缓存首次接收 | 1.465 → 1.426 | 2.818 → 2.536 | 17.412 → 17.297 | 3.328 → 3.105 |
| 首次 160 方块/秒往返 | 2.406 → 2.393 | 5.525 → 5.440 | 17.594 → 17.617 | 3.153 → 3.128 |
| 静止 | 0.565 → 0.558 | 1.048 → 1.076 | 15.768 → 15.808 | 0.386 → 0.412 |
| 再次 160 方块/秒往返 | 1.989 → 1.982 | 4.222 → 4.164 | 16.739 → 16.774 | 2.884 → 2.853 |

静止 CPU 回合范围旧版 0.350～0.436、新版 0.382～0.444，存在重叠；渲染调用平均值没有变差，不能把 0.026 核差异确定归因于修复。反复往返节点线程平均为旧版 0.005250、新版 0.005537 核，绝对差约 0.000287 核。各修复版本的三轮全部覆盖检查为 0 缺口，无异步节点/接收异常；旧版一轮最终仍有 9 列无数据，已记录，未把少做工作当作更优算法。只取旧版完整的两轮，其再次往返服务端 CPU 平均 0.367 核，与三轮 0.364 核相近，不改变开销结论。

全部高速及静止窗口均没有 >33.33 ms 帧；新版冷接收三轮合计 1 帧 >33.33 ms，没有 >50 ms 帧。限帧条件及三轮样本量不支持宣称所有硬件或整合包均没有 FPS 影响。

接收内存没有增加：首次高速峰值的三轮平均 30.30 → 29.13 MiB，再次高速 31.85 → 30.75 MiB。新版最高接收队列 338/512、请求 151/512，停止后接收和网格排空。新版三轮最大接收预留内存 31.75 MiB，远低于 128 MiB 配置。队列是每秒样本峰值，不是瞬时全量峰值。

反复往返 CPU 范围旧版 0.346～0.388、新版 0.410～0.508，差异稳定。窗口内服务端转换完成数平均约 57 → 1730 列；首次往返约 367 → 1133 列。原版发送的新版本现在进入持久失效流程，区块卸载清理内存版本后也不会复活旧缓存，所以反复跨越原版加载边界仍可能重新刷新，不能把它只称为一次性成本。相同版本重复发送仍复用已有版本。

新增状态维护本身不在每帧扫描整树：节点转换时最多检查 8 个直接兄弟节点，缺口核验复用现有捕获流程，失效沿用 dirty 批次及后台限速。没有为了微小波动新增线程、缓存格式、重试机制或牺牲版本一致性。本场景无需进一步性能补丁；若真实多人服长时间高速移动接近 CPU/IO 上限，需要另测并发刷新吞吐和磁盘压力。

先按 `docs/coarse-lod-recovery-2026-10-07.md` 的输入方式准备 `build/coarse-recovery-input`。比较脚本运行两边原始生产 class/resources 和同一份当前 smoke 监测代码；launch 参数分别引用各自 Gradle classpath，避免混用版本。每轮输出摘要后立即删除本轮游戏/缓存/完整日志，失败则保留单轮现场供定位。

消融审查保留实际需要的渲染调用计时、实际窗口限帧状态与显式窗口上限设置、四阶段路线和对照摘要；没有修改生产渲染算法。覆盖结果单独记录，即使旧版有缺口也保留实测开销，新版必须完整才能作为通过结果。预试修正了测试脚本读取旧 `cruise_done` 的完成竞态；被丢弃的预试不混入正式统计。当前 smoke 代码编译通过，新增脚本语法检查通过，`--mode request --launch-build build` 的真实接收流程回归通过，两 JVM 正常退出。
