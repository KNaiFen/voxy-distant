# voxy-distant 正常游玩问题审查

审查日期：2026-10-09。审查版本：`0.2.27-forge-1.20.1`，基线提交：`976ba84c10388752f36ab6075dc7a52809a4342b`。

本次发现 **3 项有明确代码依据的问题：1 项 P1、2 项 P2**。优先修复死亡重生后的玩家会话，其次修复维护结束后的扫描恢复。第三项会带来不必要的单人世界后台负载，实际卡顿程度需另做性能测量。本次只审查并提交文档，未修改生产代码。

检查了多人远景会话、维度切换、请求与取消、分片与合批、区块失效通知、缓存持久化、单人世界生成、索引重建，以及部分 Voxy/Embeddium 渲染和保存衔接。使用仓库 CodeGraph 追踪调用链，并对照项目固定的 Voxy 源码与当前构建使用的 Minecraft/Forge 类。

- **P1**：常见游玩操作后，主要功能持续失效，应优先修复。
- **P2**：特定正常操作后功能异常，或产生可避免的后台负载，应安排修复。
- **代码确认**：触发路径与错误状态能由当前生产代码和依赖实现直接确定。
- **方法级复现**：直接调用当前编译后的生产方法，使用最小上下文检查状态；不等同于真实客户端完整游玩复现。

本次未启动真实客户端或专用服务器，未做新的画面、帧率或 TPS 测量。因此，下文将已验证的状态错误与建议进行的实机验收分开列出，不把推导出的画面表现写成已经拍摄或测得的结果。

## VD-01：死亡重生后继续使用旧 ServerPlayer

**定位**

- `src/main/java/dev/voxydistant/server/RemoteServer.java:222`：`Session.player` 是 `final ServerPlayer`。
- `RemoteServer.java:241–247`：构造时保存玩家及维度；注册登录、退出、换维度事件，没有重生事件。
- `RemoteServer.java:282–286`：按 UUID 使用 `computeIfAbsent`，不会替换同 UUID 的旧会话。
- `RemoteServer.java:300–345`：请求按新玩家 UUID 找到旧会话，范围判断使用 `s.player.chunkPosition()`。
- `RemoteServer.java:690`：从 `s.dimension` 构造缓存/生成任务的维度键。

**原因与影响**

Minecraft 重生会新建一个 `ServerPlayer`，保留 UUID 和连接。当前 Forge 1.20.1 的 `PlayerList.respawn` 第 440 行创建新玩家，第 485 行替换 UUID 映射，第 488 行发送 `PlayerRespawnEvent`；该方法不发送 `PlayerChangedDimensionEvent`。本次通过 `PlayerList.class` 的 SHA-256 匹配，确认用于核对的源码与项目实际编译依赖中的类一致。

远景会话没有跟随这次对象替换。随后 `accept()` 虽然收到的是新玩家，仍通过 UUID 取出旧 `Session`，且不会更新 `player` 或 `dimension`。

同维度重生时，远景请求继续以死亡位置为中心做范围判断。若死亡点距离床或出生点超过接收半径，新位置附近的正常请求就会得到 `out_of_range`。即使重生距离较近，远景可用范围也会逐渐与玩家实际位置错开。

跨维度重生时，旧会话和 Hello 仍指向死亡维度。客户端 `RemoteClient.tick()` 第 170 行要求 Hello 维度与当前世界一致，因此可直接停在不接收新维度远景的状态。旧会话本身的任务也仍使用旧维度。

**复现/验收场景**

1. 使用装有本 Mod 的专用服务器或 LAN 访客，确认已开始接收远景。
2. 将接收半径设为 64 区块，在主世界设置出生点；远离出生点超过 128 区块后死亡并重生。
3. 在出生点移动并观察远景请求；检查服务端会话中的玩家对象是否等于玩家列表中的当前对象，检查 `out_of_range` 回复。
4. 再覆盖“下界死亡、主世界重生”，检查是否收到主世界 Hello。

**修复建议**

处理 `PlayerRespawnEvent`，解绑旧会话的需求并用重生后的玩家重建会话、重新发送 Hello，复用现有 `removePlayer` / `addPlayer` 生命周期即可。不能只替换 `player`，因为维度、原版区块集合和在途任务也属于旧会话。

**临时绕过**：退出服务器后重新连接。普通传送不会替换会话中的旧玩家引用，不能作为可靠绕过方式。

**验证状态**：代码确认；尚未执行真实死亡重生客户端验收。

## VD-02：维护或索引重建后，静止玩家不会重新建立发现目录

**定位**

- `src/main/java/dev/voxydistant/client/RemoteClient.java:51–64`：维护状态变化和 `indexRebuilt()` 都会设置 `s.x = Integer.MIN_VALUE`、清空 `discovery`。
- `RemoteClient.java:236–243`：重新扫描的条件包含 `s.shape == null`、传送、半径/视距变化、移动版本变化，却不包含 `s.x == Integer.MIN_VALUE`。
- `src/main/java/dev/voxydistant/client/RegionDiscovery.java:46`：`reset()` 清空区域及自身 `shape`，不会清除外层 `Session.shape`。
- `src/main/java/dev/voxydistant/server/RemoteServer.java:1202`：导入结束向在线玩家发送恢复消息。

**原因与影响**

重置逻辑使用无效中心坐标表示“需要重扫”，但 tick 的传送判断明确排除了这一坐标，重新扫描条件又没有检查它。原来的 `Session.shape` 和 `movementRevision` 仍然有效。

当玩家保持静止、半径和视距不变、索引预算足够时，整个重新扫描条件为假。`RegionDiscovery` 已经没有任何区域，后续没有区域可准备、核验或发现缺口。

导入路径还会清空待请求和重试状态，并改变 epoch。虽然 `fullRetry` 能补充一部分已有版本记录的列，但它不能替代全范围扫描，未记录版本的远景缺口仍不会发现。手动重建索引路径也会丢失发现目录；当时已在途的请求可能继续完成，但不会恢复完整扫描。

**已执行的方法级复现**

复用当前 `build/classes/java/main` 和 `build/smoke-launch.json` 的依赖。构造一个半径 64、视距 12、索引预算 256 MiB 的最小会话，先创建发现目录，再直接调用生产 `maintenance(session, false)`，随后调用生产 `tick(session, frame)`，保持移动版本不变。

关键输出：

```text
RESET_PROBE regions=0 center=-2147483648 sessionShapePresent=true stationaryMoveCondition=false
RESET_CONTROL explicitMoveRegions=18
REAL_TICK_AFTER_RESET regions=0 center=-2147483648
```

对照调用 `RegionDiscovery.move()` 能重新建立 18 个区域；当前恢复路径调用 tick 后仍为 0。探针使用最小上下文隔离扫描重建分支，没有启动游戏或实际传输数据。

**修复建议**

让重置后的状态直接满足重新扫描条件，例如在现有判断中包含 `s.x == Integer.MIN_VALUE`，或重置时清空 `Session.shape`。选择一种即可，不需要增加新的状态机。验收应覆盖导入成功、导入取消、手动重建索引后原地等待，确认无须移动便会重发范围并恢复目录扫描。

**临时绕过**：水平移动使移动预测版本发生变化，或关闭再开启“接收服务端远景”；单纯原地转动视角不会改变这里使用的位置预测。

**验证状态**：生产重置与 tick 方法级复现；完整客户端导入/命令工作流尚待验收。

## VD-03：单人生成只查询内存覆盖页，误判已有磁盘缓存

**定位**

- `src/main/java/dev/voxydistant/compat/CoverageStore.java:338–339`：`hasColumn()` 只调用 `pages.get()`，页未驻留内存就返回 `false`。
- `CoverageStore.java:261–293`：实际读取持久化覆盖记录发生在 `page()`；`hasColumn()` 不经过该路径。
- `src/main/java/dev/voxydistant/generation/GenerationController.java:217–221`：本地发现把 `!hasColumn()` 当成需要生成的条件。
- `GenerationController.java:196–202`：提交前仍用同一个内存查询，然后添加 FULL 区块 ticket。
- `GenerationController.java:225–257、319–329`：继续复制整列快照并进行转换/保存。

**原因与影响**

`CoverageStore` 重开后没有主动恢复全部内存页。对于已经完整保存在磁盘、但还未被渲染或其他操作加载覆盖页的区域，`hasColumn()` 无法区分“已有记录但未驻留”和“确实缺失”。

单人生成的两次检查都使用此方法，所以能将已有 LOD 的列再次提交为真实区块加载和转换任务。若覆盖页稍后被其他工作载入，剩余候选可能被跳过，但已经提交的任务不会因此在快照入口重新检查覆盖情况。

玩家可能在重进存档或返回旧区域时看到后台重复生成/转换，增加区块读取、CPU 和保存开销。这里的“生成”可能只是载入已存在的真实区块，**不代表重复创造新地形，也没有证据表明会损坏存档**。本次没有测量由此造成的帧率或 TPS 损失。

**已执行的方法级复现**

使用生产 `CoverageStore` 和实际 RocksDB，在 `(40,40)` 将主世界高度 `[-4,20)` 的整列标记为完整，保存并关闭，然后重新打开同一路径：

```text
LOCAL_CACHE_PROBE coldHasColumn=false afterPageLoad=true
```

重开后的 `hasColumn()` 返回 `false`；通过 `hasFull()` 显式载入覆盖该列的两个垂直页后，同一 `hasColumn()` 返回 `true`。磁盘数据没有改变，差别只在是否驻留内存。

**修复建议**

本地发现应查询持久化覆盖目录，或在受预算控制的准备阶段加载相关页，再判定是否需要 FULL ticket。已有 `directory()` / 目录精度信息可以作为实现基础；不要把全盘扫描恢复到启动过程，也不宜在服务器 tick 中为每一列无预算地同步读取磁盘。

建议验收：同一已完成单人存档关闭再打开，在覆盖页未驻留的区域检查 `LOCAL submit`，确认完整缓存列不再重复提交；同时确认真正缺失的列仍正常生成。

**临时绕过**：已有远景足够时可关闭“本地生成”，代价是不会提前生成未探索的远景。

**验证状态**：缓存判定错误已方法级复现；后台任务提交影响由调用链确认，实际负载大小尚未实测。
